● 我基本定位到问题了。_c_int00_sbl 来自
  boot_armv7r_asm.obj（nortos.awr2x44p.r5f.ti-arm-clang 库）。从 map
  的符号布局可以确认它的语义：

  10206b8c  _c_int00_sbl      ← 你设的入口（精简入口）
  10206ba4  _sblLoopForever
  10206bac  _c_int00_addr     (.word _c_int00)
  10206bb0  _c_int00          ← 完整入口
  10206c60  bypass_auto_init  ← 在 _c_int00 内部，靠近末尾

  核心结论：_c_int00_sbl 会跳过 C 运行时初始化（auto-init）

  这两个入口的区别就在 bypass_auto_init 这个标号：

  - _c_int00（完整入口）：建栈 → MPU/Cache → 执行 __TI_auto_init：处理 .cinit 
  记录，把 .data 从 load 地址拷到 run 地址、把 .bss 清零 → 跳 main。
  - _c_int00_sbl（SBL 精简入口）：直接跳到 bypass_auto_init，跳过 .data 拷贝和 
  .bss 清零。它的前提是"加载器（SBL）已经替我把这些段初始化好了"。

  你的 map 里明确有这些 cinit 记录，是要在运行时被处理的：

  .cinit..data.load                          ← .data 需要从 load 拷到 run
  .cinit..bss.load  compression = zero_init  ← .bss 需要运行时清零

  如果你直接从 _c_int00_sbl 进，而加载器又没替你做这两件事，那么所有 
  .bss/零初始化全局变量都是上电随机值，.data 也是未初始化的垃圾。

  为什么现象正好是"卡在 idle、没有 CAN"

  .bss 没清零的直接后果：
  - FreeRTOS 的堆 ucHeap、uxCurrentNumberOfTasks、各任务/队列句柄全在 .bss →
  xTaskCreate/xQueueCreate 创建应用任务时拿到垃圾指针/计数，创建失败或行为异常 →
  只剩 idle（和 Tmr Svc）能跑 → R5 永远在 prvIdleTask。
  - AUTOSAR 的状态机（EcuM/BswM/CanSM 的 state、"已初始化"标志位）是垃圾 → CAN
  通道永远进不到 RUN 态，Com 周期 MainFunction 推不动 → 没有 CAN 输出。
  - 电流能上来且跳动：因为早期 CPU/时钟/RF 前端那部分（SBL
  已做或精简入口仍走到）跑到了，但上层逻辑全废了。

  也就是说，换 _c_int00_sbl
  只是"骗过了"之前卡住的那一段，并没有真正修好——它把启动初始化整段跳过了。

  elf2rprc.js 揭示了 BM 的加载契约

  看 elf2rprc.js 里 elf2rprc_sections 的核心几行：

  let h = readElfSectionHeader(r, a);
  h = h.filter(t => !(8 & t.sh_type));   // 排除 SHT_NOBITS（type=8，就是 .bss）
  h = h.filter(t => 2 & t.sh_flags);     // 只保留 SHF_ALLOC 段
  ...
  o(c, a.e_entry, 4, s);                 // RPRC 头里的入口 = ELF 的 e_entry

  这说明两件致命的事：

  1. BM 跳转的地址 = 你 ELF 的 entry（即 --entry_point）。你把 entry 设成
  _c_int00_sbl，BM 加载完段后就直接跳进 _c_int00_sbl——绕过 vectors、绕过
  auto-init。
  2. .bss 被显式过滤掉，根本不进 RPRC 镜像（!(8 & sh_type)）。也就是说 BM 
  不会、也没法替你清 .bss。

  再看你自己的 linker map：.data 0 10216000 00000fb0 UNINITIALIZED —— 你用的是
  --rom_model / -c（ROM 自动初始化模型），.data 运行段是 UNINITIALIZED，初值放在
  .cinit 里，必须靠 app 自己的 auto-init 在运行时把 .cinit 拷进 .data、把 .bss 
  清零。

  所以 _c_int00_sbl 在 BM 启动下是错的

  链条对上了：
  - BM 不清 .bss、不展开 .cinit → .data/.bss 全是上电垃圾；
  - _c_int00_sbl 又故意跳过 auto-init（跳到 bypass_auto_init）；
  - 结果 FreeRTOS 堆/AUTOSAR 状态机全是垃圾 → 应用任务建不起来、CAN 栈进不了 RUN
  → 只剩 idle、没有 CAN。

  _c_int00_sbl 只有在"加载器已经替 app 把 .data/.bss 初始化好"时才能用。TI
  的某些 SBL 场景是这样，但你这个 BM 不是（.bss 直接被 elf2rprc 扔了）。

  正确做法：入口要指向"会跑 auto-init 的启动代码"

  你工程里其实已经为此准备好了入口——bswpf/ld/TPR12_MCU_LS.lds 第 11 行就是：

  --entry_point=InitAdjustingEntry

  而 InitAdjustingEntry（在 bswpf/mcal/integration/ResetHandler.s）做的正是 BM
  启动需要的全套：

  InitAdjustingEntry:
    ... 使能 VFP/NEON ...
    ... 切到 SYSTEM 模式 ...
    ... 初始化 system 栈 ...
    bl  _c_int00 + 40     ; 跳过 _c_int00 头40字节(VFP+切user模式)，但仍执行完整
  auto-init

  _c_int00 + 40 会执行 完整的 cinit 处理（拷 .data + 清 .bss），然后进 main →
  EcuM_Init。这条路不依赖向量表取指，无论被 TI SBL 还是 BM
  跳进来都能自洽，而且它特意停在 SYSTEM 特权模式（RTA-OS/AUTOSAR
  需要），这就是工程不用裸 _c_int00（裸 _c_int00 头40字节会切到 user
  模式）的原因。

  改法：把 entry 从 _c_int00_sbl 改回 --entry_point=InitAdjustingEntry。 保留
  -u=_c_int00（lds 第9行已有，确保 _c_int00 被拉入）。--undef_sym=_vectors 
  --retain="*(.vectors)" 这两条对 BM 没用，可以去掉（你的异常表是 RTA-OS 的
  .Os_ExceptionVectorTable，不是 .vectors）。

  顺带解释你看到的现象：
  - -e_vectors 在 BM 下大概率"电流都起不来"——因为 BM 直接跳到向量表地址，而这里
  0x4 处是 RTA-OS 的异常表、首条不是合法的"跳启动代码"指令，立刻跑飞；
  - 换 _c_int00_sbl 是真代码，能往下跑（电流起来、RF 在动），但跳过了
  auto-init，上层全废 → 卡 idle。两个现象都和这个模型一致。

  跳转时如果已经使能了 MPU/Cache 或处于某个特定模式，理论上 _c_int00
  会自己重设，一般没问题（这是 TI mmWave SDK 的标准启动路径，TI 官方 SBL 也是跳

  InitAdjustingEntry 风格的薄 shim（先 VFP、切 SYSTEM 模式、建栈，再 bl _c_int00
