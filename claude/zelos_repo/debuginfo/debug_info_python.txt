  ---
  🔴 必须处理

  1. .text/.rodata 未路由,落进几乎满载的 MSS_L2(链接风险)
  linker.cmd 只路由了 .bss.wfNoInit 和 .bss.wfDbgStack。wf_debug_info.oer5f
  的代码段(~几 KB)和 gWfDbg(~250B)、frame[64] 都被平台 catch-all 收进
  MSS_L2。这正是触发 GROUP_6 碎片化链接错误的典型场景。建议补:
  .wfDbgCode: { wf_debug_info.oer5f(.text)  wf_debug_info.oer5f(.text.*)
                wf_debug_info.oer5f(.rodata) wf_debug_info.oer5f(.rodata.*) } >
  TCMA_RAM
  .wfDbgData: { wf_debug_info.oer5f(.bss)   wf_debug_info.oer5f(.bss.*)
                wf_debug_info.oer5f(.data)  wf_debug_info.oer5f(.data.*) }  >
  TCMB_RAM

  重叠——TI 链接器按最具体匹配,已命名段会优先,但稳妥起见把 .wfDbgData
  放在那两行之后,或改用 EXCLUDE。这点编译时要盯一下。

  ---
  🟡 真实但低概率的缺陷

  2. wf_debug_mark_can_tx_stall 对 faultSummary 的 |= 
  没有临界区保护(wf_debug_info.c:321-325)
  gWfDbg.faultSummary |= WF_DBG_FAULT_CAN_TX_STALL;   // 裸 RMW
  文件里已有现成的 wf_dbg_set_fault()(带 HwiP_disable)。这个函数从 CAN
  路径调用,可能与 RSP 任务里 snapshot 的 faultSummary |= 并发,丢位。直接改成
  wf_dbg_set_fault(WF_DBG_FAULT_CAN_TX_STALL) 即可。

  3. framePeriodMaxDev100us 写无锁、page0 读后清零有锁——非对称,可能丢一个采样
  wf_debug_mark_stage(可能在 DPM report/SWI 上下文)裸写 max,wf_dbg_build_page0
  在 HwiP_disable 内读取并清零。若两者交错,会丢一次峰值更新。影响是"少记一帧抖动
  ",可接受,但若要严谨,mark_stage 的 max 更新也应进临界区。

  ---
  🔵 设计注记(非 bug,确认是否符合预期)

  4. 黑匣子记录直到 POR 才清。recType 在 noinit RAM,一旦命中 assert,之后每次 
  warm boot 都会 bbFromPrevBoot=1 + 置 BLACKBOX
  故障位,即使那次崩溃已经过去很多个启动周期。bbFromPrevBoot 能区分"本次 vs
  往次",但没有"读取 N
  次后清除"机制。如果你想要的是"上一次启动是否崩溃",当前逻辑是"自上次 POR
  以来是否崩溃过"。

  5. noinit 跨复位保留能力 = 硬件待验证(最高优先级验证项)。.bss.wfNoInit 
  (NOLOAD) 能否真的不被启动清零,取决于 TI Arm-Clang autoinit 是否把它并入 BSS
  清零、以及 SBL 是否对 TCM 做 ECC 清零。代码注释和 skill
  都已标注。上板第一件事:故意触发一次 assert → warm reset → 看 Page3 的
  bbFromPrevBoot/line/fileHash 是否还在。如果被清了,黑匣子整套就是哑的。

  6. WF_DBG_TASK_COUNT=6 但只有 5 个任务(bit5 预留)。无害,bit5 不在 expect
  掩码里,不会误判死。

  ---
  一、一切设计的出发点:一个硬约束

  实车上只有一条 CAN 总线,接不了调试器。 出了问题你看不到内存、看不到栈、打不了
  断点。所以唯一的办法是:让固件自己定期把"体检报告"通过 CAN 播出来,你在总线上用
  CANoe/CANalyzer 收。

  这条报文(0x200)就成了你唯一的眼睛。它本身的设计质量,直接决定了出问题时你能不能
  定位。

  ---
  二、核心矛盾:信息太多,带宽太小

  - 想监测的东西几十项(各阶段耗时、丢帧、温度、CAN 健康、栈、复位原因……)。
  - 但 CAN FD 单帧最大只有 64 字节(DLC=15),装不下。

  解法 = 分页轮播(multiplexing)。 Byte0 低 4 位当"页号",每 66ms 发一页,4 页一轮:

  t=0ms   发 Page0(时序)
  t=66ms  发 Page1(数据通路/RF)
  t=132ms 发 Page2(TimeSync/CAN)
  t=198ms 发 Page3(黑匣子/栈)
  t=264ms 又回 Page0 ...

  264ms 拿到一张完整快照,总线上只占一条周期报文,负载不变。这是 debug
  日志的理想形态。

  ---
  三、五条"立规矩"的设计原则(方法论精华)

  这几条是把"实时状态"变成"可靠日志"的关键,也是这套东西和普通打印 log
  的本质区别:

  原则: ① 粘滞位(sticky)
  为什么: 两次报文间隔
    66ms,中间发生的瞬态故障(比如一次超时尖峰)如果只报"此刻状态"就漏了。所以故障
  位用"或累加",只置不清,只要本上电周期发生过就一直为
      1
  代码体现: faultSummary |= bit,整个 wf_dbg_set_fault()
  ────────────────────────────────────────
  原则: ② 峰值锁存 + 读后清零(max-hold)
  为什么: 算法超时是偶发尖峰,报平均值会被抹平。所以各阶段耗时报"这个窗口内的最大
  值",发出去后清零,重新抓下一窗口的尖峰
  代码体现: tMax[i],page0 发完 tMax[i]=0
  ────────────────────────────────────────
  原则: ③ 滚动计数器 + CRC
  为什么: rolling counter 每帧 +1 → 丢帧/总线阻塞一眼可见;帧尾 CRC16 →
    防误码。和你的 TimeSync 帧同一套路
  代码体现: rollingCounter,wf_dbg_crc16
  ────────────────────────────────────────
  原则: ④ 公共头每页都带
  为什么: rolling
    counter、故障摘要这种"一眼定生死"的信息,每一页都要带。否则带它的那一页一丢你
  就瞎了
  代码体现: 每帧 Byte0–5 固定头
  ────────────────────────────────────────
  原则: ⑤ 采集/发送解耦
  为什么: 采集点(算法流水里)绝不能做阻塞发送;发送放独立任务。这样即使 canoutput 
    任务挂了,这条报文照样能发出来并报告"它挂了"
  代码体现: 独立 wf_debug_info_task,66ms 自己跑

  四、架构:数据怎么流动

     算法流水线(RspTask / DPM reportFxn)          独立发送任务(66ms)
     ┌─────────────────────────────┐            ┌──────────────────────┐
     │ 每帧/每阶段调用"采集 API":   │            │ 1. 评估存活/健康      │
     │  mark_stage()  ← 走到哪一阶段│  写入全局   │ 2. 填公共头           │
     │  frame_snapshot() ← 耗时快照 │ ─────────► │ 3. 按当前页号填载荷    │
     │  task_alive()  ← 任务心跳    │  gWfDbg    │ 4. 算 CRC             │
     │  mark_vehicle_rx() 等        │            │ 5. 发 0x200,翻页      │
     └─────────────────────────────┘            └──────────────────────┘
          (短临界区,不阻塞)                       (HwiP 临界区读全局快照)

  - 采集端:散落在各处的单行埋点,只更新内存里的全局结构 gWfDbg,极轻量。
  - 发送端:一个独立 FreeRTOS 任务,66ms 醒一次,把 gWfDbg 打包发出。
  - 中间用 HwiP_disable/restore(关中断临界区)保证读写一致 ——
  这就是你刚让我加锁的 fix #2/#3 在补的地方。

  ---
  五、帧格式

  公共头(每页 Byte0–5 都一样):
  [0]   schemaVer(高4位) | pageId(低4位)
  [1]   rollingCounter         ← 每帧+1
  [2-3] faultSummary           ← 12 个粘滞故障位,一眼定生死
  [4]   sensorState | timeSyncState
  [5]   taskAliveBitmap        ← 各任务存活位
  ...载荷 Byte6–61...
  [62-63] CRC16

  故障摘要 12 位(WF_DBG_FAULT_*):超时、丢帧、SyncLost、CAN
  错误、过温、DTC、任务挂死、栈低、黑匣子有记录、车身超时、assert 命中、CAN-TX
  阻塞。收报文第一眼只看这 2 字节,哪一位亮了再去翻对应那一页看细节。

  4 页载荷:

  ┌───────┬───────────────────────────────────────────────┬──────────────────┐
  │  页   │                     内容                      │    答什么问题    │
  ├───────┼───────────────────────────────────────────────┼──────────────────┤
  │ Page0 │ 各阶段耗时                                    │ 慢不慢?卡哪一段? │
  │       │ max-hold、margin、超时计数、lastStage         │                  │
  ├───────┼───────────────────────────────────────────────┼──────────────────┤
  │ Page1 │ frameTrigger/result                           │ 断流没?致盲没?   │
  │       │ 计数、cfar/航迹/干扰数、温度                  │                  │
  ├───────┼───────────────────────────────────────────────┼──────────────────┤
  │ Page2 │ TimeSync offset/CRC/DTC、CAN TEC/REC/bus-off  │ 同步/总线健康?   │
  ├───────┼───────────────────────────────────────────────┼──────────────────┤
  │ Page3 │ 复位原因、黑匣子(死在哪行)、栈水位、uptime    │ 死过没?死在哪?   │
  └───────┴───────────────────────────────────────────────┴──────────────────┘

  六、几个巧妙的检测手法(值得记住)

  1. 死字段改派生计算:TI 自带的 interFrameProcessingMargin
  全工程没人填(死字段)。改成自己算:margin = 660 − mssTimeRecord[5](0.1ms
  单位,66ms=660)。教训:用一个字段前先确认它真被填充。
  2. lastStage 指认卡点:每个流水阶段写一个枚举值。一旦卡死,这个字节冻结在最后到
  达的阶段,直接告诉你卡在 CM4 还是 DOA
  还是后处理。一行代码,解决"只知道没出结果、不知道卡哪"的盲区。
  3. CAN 健康要主动轮询:MCAN_getErrCounters 原本只在"收到报文时"读 —— 可 bus-off
  时根本收不到报文,永远读不到。所以改在 66ms 发送任务里主动读 + 读
  protocolStatus(bus-off 标志在那)。
  4. 任务存活位图:每个任务在自己主循环里 task_alive() 自增一个
  tick,发送任务检查"这个 tick
  有没有在涨"。某个任务挂了但系统没崩,这是唯一能看出来的方式。
  注意区分:周期性任务(canout/timesync)才判死,事件驱动的(canrec)只进位图不判死。
  5. 栈水位扫描:静态栈数组从栈底往上数连续的
  0x00/0xA5A5A5A5,数到第一个非空字就是用过的最深处 → 算出剩余余量。

  ---
  七、黑匣子(noinit 段技巧)—— 最精彩的一招

  问题:release 下 assert 命中 = 死循环 → 雷达静默消失,什么都留不下。

  手法:
  1. 链接脚本里开一小块 .bss.wfNoInit (NOLOAD) —— warm reset 后不被清零的 RAM。
  2. 自定义 assert 钩子 wf_debug_blackbox_assert() 把 文件名hash + 行号 + magic
  写进去。
  3. 复位重启后,init 检查 magic 有效 → 说明上次是崩溃复位 → 把"上次死在哪行"通过
  Page3 发出来。

  配合 WDT(挂死→看门狗复位→Page3 报 MSS_WDT
  复位原因)就闭环了:没有任何"永久静默且无痕"的故障模式(唯一物理无解的是 bus-off
  进行中的那个窗口,靠恢复后的粘滞计数补侦)。

  ▎ ⚠️ 这招的前提是 noinit RAM 真不被清零 —— 这正是要上硬件验证的头号项,也是 WDT
  ▎ 第④步还没做的原因。

  ---
  八、你怎么用它定位问题(实战流程)

  收到 0x200 → 看 faultSummary 哪位亮
    ├ 超时位亮      → 等 Page0,看哪段 max-hold 爆了
    ├ 丢帧位亮      → 等 Page1,看 trigger 涨但 result 停 = DSP 挂了
    ├ 任务挂死位亮  → 看 aliveBitmap 哪个任务的位灭了
    ├ 黑匣子位亮    → 等 Page3,fileHash+line = 上次死在哪行
    └ rollingCounter 不连续 → 丢帧或总线阻塞

  一句话总结方法论:用一条周期 CAN 报文当"飞行记录仪",靠粘滞位抓瞬态、max-hold 
  抓尖峰、分页换带宽、心跳测存活、noinit 
  留遗言,把一个没有调试器的实车系统变成可观测的。

● 不必须,而且对你这个场景,Python 
  脚本反而是更对的选择。理由是这条报文的核心价值在 DBC 恰好做不到的地方:

  DBC mux 的天花板

  DBC(CANoe/CANalyzer)本质是单帧解码器 ——
  它能把"这一帧的这几个字节"翻成带名字的信号,但它不会跨帧、跨时间推理。而你这套
  debugInfo 最关键的诊断恰恰是跨帧的:

  - "trigger 在涨但 result 停了" → 要对比两个计数器的变化趋势
  - "rollingCounter 不连续" → 要看帧间连续性
  - max-hold、粘滞位的语义是"这段时间内发生过" → 要在时间轴上看
  - 4 页轮播 → 要把 4 帧重组成一张完整快照(DBC 每页只能各管各的,拼不起来)

  这些 DBC 全做不了,得靠脚本。

  各自真正适合的场景

  ┌──────────────────────────────────┬────────────────┬────────────────────┐
  │                                  │    DBC mux     │    Python 脚本     │
  ├──────────────────────────────────┼────────────────┼────────────────────┤
  │ 单帧字段解码                     │ ✅ 原生        │ 要自己写           │
  ├──────────────────────────────────┼────────────────┼────────────────────┤
  │ 跨页重组 / 趋势 / 连续性         │ ❌ 做不到      │ ✅ 强项            │
  ├──────────────────────────────────┼────────────────┼────────────────────┤
  │ 粘滞位 → 可读名、黑匣子 fileHash │ ❌ 只给原始值  │ ✅ 任意加工        │
  │  反查                            │                │                    │
  ├──────────────────────────────────┼────────────────┼────────────────────┤
  │ 在 CANoe GUI 实时看              │ ✅             │ ❌(需先抓 asc/blf  │
  │                                  │                │ 再跑)              │
  ├──────────────────────────────────┼────────────────┼────────────────────┤
  │ 给域控/他人用标准工具看          │ ✅             │ 要分发脚本         │
  ├──────────────────────────────────┼────────────────┼────────────────────┤
  │ 跟固件 schema 同步维护成本       │ 高(手写 mux    │ 中                 │
