  ---
  ⚠️ 先纠正一个硬约束：CAN FD 单帧最大 64 字节，不是 128

  CAN FD 的 DLC 最大就是 64 字节（DLC=15）。你定的 128
  字节在单帧里发不出去。你自己工程里的 TimeSync 帧（wf_time_sync.h）就是
  MCAN_DATA_SIZE_64BYTES / DLC=15，这是上限。

  所以 0x200 有三条路：

  ┌─────────────────┬────────────────────────┬──────────────────────────────┐
  │      方案       │          做法          │             评价             │
  ├─────────────────┼────────────────────────┼──────────────────────────────┤
  │ A. 砍到 64 字节 │ 精选信息塞进单帧       │ 最简单，但 debug             │
  │                 │                        │ 信息天然想要更多             │
  ├─────────────────┼────────────────────────┼──────────────────────────────┤
  │ B. 多路复用分页 │ Byte0 当 page/mux，每  │ DBC 里配成 multiplexed       │
  │ （推荐）        │ 帧发一"页"，66ms 轮换  │ signal，总线负载不变，能暴露 │
  │                 │ N 页                   │ 海量信息                     │
  ├─────────────────┼────────────────────────┼──────────────────────────────┤
  │ C. ISO-TP       │ 把 128B 拆成多帧重组   │ 对周期性日志属于过度设计，不 │
  │ 分段传输        │                        │ 推荐                         │
  └─────────────────┴────────────────────────┴──────────────────────────────┘

  强烈建议走 B（分页轮播）。这恰恰是 debug 日志的理想形态：每页 63
  字节有效载荷，4 页 → 264ms 拿到完整快照，对定位问题足够快，而总线只占一条周期
  报文。下面的字段目录就是按"分页"组织的。

  ---
  设计原则（架构层面，先立规矩再填字段）

  实车不能接调试器，这条报文是你唯一的眼睛，所以它本身的设计质量决定了它能不能定
  位问题：

  1. 粘滞位（sticky / latched fault bits） —— 故障摘要字用"或累加"，发出后才清。
  否则两次报文之间(66ms)发生的瞬态故障会被漏掉。这是车载日志和实时状态最大的区别
  ：你要的是"这段时间内发生过吗"，不是"此刻还在吗"。
  2. 峰值锁存 + 读后清零（latched-max reset-on-read） —— 各阶段耗时不要报"瞬时值
  "，要报这个窗口内的最大值，发完清零。算法超时是偶发尖峰，平均值会把它抹平。
  3. 滚动计数器 + CRC —— 跟你 TimeSync 帧一样：一个每帧自增的 rolling
  counter（丢帧/总线阻塞可见）+ 末尾 CRC-16（你已有
  wf_time_sync_calc_crc16，直接复用）。
  4. Schema 版本字节 —— 第一个字节放协议版本，固件迭代时 DBC 能兼容解析。
  5. 全页公共头 —— rolling counter、故障摘要字这种"一眼定生死"的信息，每一页都带
  ，不要只在某一页出现，否则那一页丢了就瞎了。
  6. 快照一致性 + 非阻塞 —— 在
  MmwDemo_DPC_ObjectDetection_reportFxn（帧结束点）做一次短临界区快照，CAN
  发送放到 mss_canoutput_task，绝不能在采集点做阻塞发送。

  一个可落地的 64 字节分页布局（方案 B）

  每帧固定结构，Byte0 选页，公共头每页都带：

  公共头 (Byte 0..7，每页相同)
    [0]   schemaVersion (高4位) | pageId (低4位)
    [1]   rollingCounter (每帧+1, 全局)
    [2-3] globalFaultSummary  ← 粘滞位: bit0 超时, bit1 丢帧, bit2 SyncLost,
                                bit3 BusOff, bit4 过温, bit5 DTC, bit6
  任务挂死...
    [4]   sensorState(4b) | timeSyncState(4b)
    [5]   taskAliveBitmap (各任务存活位)
    [6-7] CRC-16 占位 / 或放帧尾

  页载荷 (Byte 8..63，56 字节)

  Page 0 —— 时序/超时:
    各阶段耗时窗口最大值(CM4/DOA/后处理/CAN-TX/总) ×u16
    interFrameProcessingMargin u16, 超时溢出计数 u16,
    CPU负载 active/interframe, 帧周期抖动 u16
  Page 1 —— 数据通路/RF:
    frameTriggerReady(低32), DPM丢帧差值, cfarNum, trcNum,
    intfNum, waveId, 温度×N, anaMon故障位, failedTimingReports
  Page 2 —— TimeSync/CAN总线:
    offsetUs i32, crc/invalid/jump 计数, dtcActive+reason,
    CAN TEC/REC, busOff, TX丢帧, 车身信息同步失败计数
  Page 3 —— 异常黑匣子:
    resetReason, lastErrorCode i32, lastAssert(fileHash+line),
    uptime ms u32, watchdog余量, sensorStart/Stop计数

  公共头里的 globalFaultSummary（粘滞）让你任何一帧、任何一页都能一眼判生死；要
  细节再看轮到的那一页。

  ---
  三、四个必须补的盲区

  ① margin 死字段（已述） —— Page0 改为派生：margin = 660 − 
  mssTimeRecord[5]（0.1ms 单位），CPU load 两个字段删掉，换成"超时溢出计数 +
  上次溢出时各阶段快照"。

  ② 没有看门狗 —— mss.syscfg 里没配 WDT。意味着场景 4/12 的挂死 =
  雷达永久静默，连复位重启的机会都没有，debugInfo 也跟着消失。建议把 MSS WDT 
  使能（syscfg 里加 watchdog 模块，在 66ms 发送任务里喂狗）——挂死 → WDT 复位 →
  重启后 Page3 报
  SOC_WarmResetCause_MSS_WDT，闭环了。这是让整套方案"兜底"的一块拼图。

  ③ 栈/堆监控缺失 —— 实车偶发踩内存是嵌入式头号疑难。补三个信号（都是 FreeRTOS
  现成 API，每 66ms 读一次几乎零开销）：
  - 各关键任务 uxTaskGetStackHighWaterMark() 的最小值（u8，剩余字数/16）
  - xPortGetFreeHeapSize() / xPortGetMinimumEverFreeHeapSize()
  - vApplicationStackOverflowHook 里置粘滞位 + 记任务号（FreeRTOSConfig 需开
  configCHECK_FOR_STACK_OVERFLOW=2）

  ④ assert/崩溃黑匣子（noinit 段技巧） —— 在链接脚本加一小块 .noinit 段（warm 
  reset 不清零的 RAM），自定义 assert 钩子把 文件名hash+行号+magic
  写进去再触发复位（或等 WDT）。重启后开机检查 magic 有效 → Page3
  把"上次死在哪一行"发出来。这是没有调试器的实车上唯一能把"死前最后一口气"带出来
  的手段，强烈建议做。你工程的 MmwDemo_debugAssert
  宏（mmw_mss.h:625）是统一入口，改一处全工程生效。

  ---
  四、修正后的 v2 页面布局

  公共头 Byte0..5 (每页带) ：
    [0] ver(4b)|pageId(4b)  [1] rollingCounter
    [2-3] globalFaultSummary 粘滞位:
          bit0 超时发生过      bit1 丢帧(trigger-result差值>0)
          bit2 SyncLost        bit3 CAN errorPassive/busOff曾发生
          bit4 过温            bit5 DTC active
          bit6 任务失活        bit7 栈溢出hook触发
          bit8 黑匣子有记录    bit9 车身信息超时
    [4] sensorState(4b)|timeSyncState(4b)
    [5] taskAliveBitmap
  Byte62..63 = CRC16 (复用 wf_time_sync_calc_crc16)

  Page0 时序: 各阶段耗时max-hold×7(u16,0.1ms) + 派生margin(i16)
             + 超时计数(u16) + 上次超时帧号(u32) + lastStageReached(u8)
             + 帧周期实测max偏差(u16)
  Page1 数据通路/RF: frameTriggerReady(u32) + result计数(u32) + cfarNum
             + trcNum + intfNum + waveId + 温度×4(i8) + failedTimingReports
             + anaMon故障位 + 车身报文age(u16,ms) + 车身同步失败计数
  Page2 TimeSync/CAN: offsetUs(i32) + crc/invalid/jump计数 + dtcReason
             + TEC/REC(u8×2) + protocolStatus + busOffEverCount
             + TX丢帧计数(各CAN实例)
  Page3 黑匣子/资源: resetCause + warmResetCause + uptime(u32)
             + 黑匣子assert记录(fileHash u16+line u16+count u8)
             + 各任务栈最小余量×6(u8) + minEverFreeHeap(u16,/64B)
             + lastErrorCode(i32) + sensorStart/Stop计数

  诊断闭环现在是完整的：慢(Page0) → 断流(Page1) → 总线/同步(Page2) → 
  死过(Page3黑匣子)，加上 WDT 兜底后没有"永久静默且无痕"的故障模式了（唯一例外是
  bus-off 进行中的窗口，物理上无解，靠恢复后的粘滞计数补侦）。

  1. 0x200 报文基本收发：CANoe/CANalyzer 收四页轮播，rollingCounter 连续、CRC
  对（CRC 参数与你 TimeSync 0x040 完全一致，校验范围 Byte0..61）

  数值对得上（单位 0.1ms）
