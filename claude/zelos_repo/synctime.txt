  改动总结

  改了 wf_time_sync.c 三处，核心是把解析从「只认扩展帧」改成「按 CAN‑FD
  标准帧解析」，并加了调试日志。

  1. 根本 bug 修复 — wf_time_sync_parse_frame

  原逻辑有两个问题，导致标准帧 TimeSync 报文永远匹配不上：
  - if (rxMsg->xtd == 0U) return NOT_MATCH; —— 直接拒绝所有非扩展帧；
  - rxMsg->id & 0x1FFFFFFF 和 0x040 比较 —— 但标准 11‑bit ID 在 MCAN RX buffer
  里是左移 18 位存放的（和 mss_mcan.c:566 的 (id >> 18) & 0x7FF
  一致），所以即使去掉 xtd 判断也对不上。

  现在改为：
  - 去掉 xtd==0 拒绝逻辑，扩展帧 / 标准帧都做兼容提取 ID（标准帧用 >> 18
  还原），但只匹配 WF_TIME_SYNC_CAN_ID(0x040)；
  - 保留 fdf==1(必须是 CAN‑FD) 和 DLC 校验，且各自带日志说明被丢弃的原因。

  新增了两个宏 WF_TIME_SYNC_STD_ID_SHIFT (18U) 和 WF_TIME_SYNC_STD_ID_MASK 
  (0x7FF)。

  2. 收包/解析日志 — wf_time_sync_handle_canfd
  - 每收到一帧打印 rawId / xtd / fdf / dlc / 当前状态，确认是否收到报文；
  - 解析失败时打印 status 和累计 invalid/crc 计数；
  - 解析成功时打印 seq / status / GT 秒.纳秒。

  3. 状态机日志 — wf_time_sync_process_frame
  - 进入处理时打印 seq / state / firstSync / silentWait / sensorStarted / 
  offset；
  - 命中「异常2 本地时钟跳变」分支时打印 delta 与阈值。

  这样你在串口就能看到完整链路：是否收到 0x40 报文 → 是否通过 CAN‑FD/DLC 校验 → 
  解析出的全局时间 → 状态机如何决策（启动传感器 / 保持 offset / 进入 SYNCED）。

  需要注意：handle_canfd 是在 CAN
  接收回调路径里调用的，如果它运行在中断上下文中，密集的 DebugP_log
  可能影响实时性。调试完后建议把这几条收包日志降频或用宏开关包起来。要我加一个
  WF_TIME_SYNC_DEBUG 开关宏来统一控制这些日志吗？
