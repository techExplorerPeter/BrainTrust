● size 就是这帧的有效数据字节数(payload),不含 CAN 协议开销。所以 17 KB/s 是纯
  payload 速率。下面讲清楚我怎么从 284 帧/s + 17 KB/s 推出"~4%",以及准不准。

  推算方法

  CAN-FD 一帧的总线占用时间分两部分:和 payload 无关的固定开销 + payload 
  数据本身。

  ① 固定开销(每帧都有,跟字节数无关)——走仲裁段速率 1 Mbps:
  SOF + 11位ID + 控制位 + CRC界定符 + ACK(2) + EOF(7) + 帧间隔IFS(3) ≈ ~30 位 ≈ 
  30µs/帧

  ② payload 数据——走数据段速率 5 Mbps:
  每字节 8 位 ÷ 5 Mbps = 1.6µs/字节

  总线忙时间 ≈ 帧数×30µs + 字节数×1.6µs
  = 284 × 30µs  +  17408 × 1.6µs
  = 8520µs      +  27853µs
  = 36373µs / 1s  ≈  3.6%
  (我上次说 ~4%,这次拆开算 3.6%,同一量级)

  准不准:这是粗估,误差约 ±1~1.5%(绝对)

  会让真实值偏高的因素(我没算进去):
  - 位填充(bit stuffing):仲裁段每 5 个同极性位插 1 位,数据段有固定填充位 →
  实际多 ~3-8%。
  - DLC 量化:CAN-FD 超过 8 字节只能取 12/16/20/24/32/48/64,比如 17
  字节的帧上线占 20 字节槽。size 传的是请求长度,上线字节可能比统计的多。
  - 我把仲裁/控制位都按理想 1µs、数据位按 0.2µs
  算,实际采样点/传播段配置会有出入。

  结论:这个数是数量级正确的粗估(精度 ~±1.5% 绝对),足够判断"轻(4%)还是重(40%)"和
  看趋势,但不是精密总线负载表。要精确值得用真正的总线分析仪,或读 MCAN
  自己的统计寄存器。

  一个更重要的限制 ⚠️

  固件只能数雷达自己发的帧。总线上别的 ECU 发的雷达根本看不见。所以:

  ▎ 这个"CAN 负载"= 雷达自己的贡献,是整条总线负载的下限,不是全总线占用。

  实车判断"总线是不是要满了",真正可靠的信号其实是 txStall(FIFO 满等待)和
  tec/rec/busOff——那些是雷达实测到的总线背压,比我这个手算的百分比靠谱。TX
  速率那两个数用来看雷达自己发得多不多 / 有没有异常暴涨最合适。

  debugInfo 开启时的影响评估(逐项)

  1. 单帧开销:多一次 mutex take/give ≈ 几微秒 DPL 开销。对比 64B CAN-FD
  上线时间(500K/2M 下 ~278µs)可忽略。

  2. 串行化代价:canoutput 和 debug 极少同时发(debug 才 2
  帧/66ms)。真撞上时,一方等另一方的"写槽+请求"(正常 µs 级)。

  3. 最坏情况:若 FIFO(30 深)全满(=严重背压,txStall 会报),持锁方自旋等待最多
  CAN_FIFO_WAIT_MAX=20 tick ≈ 20ms,期间另一方被挡。但:
  - 这 20ms 是 FIFO 
  满这个总线状态本身造成的,不是锁新增的——没有锁时,另一方照样撞上满 FIFO
  等同样久,锁只是把"并行等"变成"串行等";
  - 优先级继承:持锁的低优任务被临时提到等待方优先级,尽快排空;
  - 只在 debug 开(开发期)发生。
     → 没有引入超出"总线已坏"状态之外的新最坏延迟。

  4. 死锁/优先级反转:
  - 优先级继承 mutex → 无无界优先级反转;
  - 单一 out: 释放、无递归、无 ISR 调用方 → 无死锁;
  - 即使 inject 的 KILL_RSP 挂起 RspTask 也不影响——RspTask 
  不调这个发送函数,挂不住锁。

  5. 内存:1 个静态 SemaphoreP_Object(≈80B 静态,无堆)。可忽略。

  6. 不触碰的东西:位率、FIFO 深度、帧 ID、帧内容、DLC、时序配置全不变。OTA

  核心设计(关键:flash 黑匣子的"预擦+只写"模式)

  因为 RAM 活不过复位,崩溃记录必须在故障当下写进 flash。但在 abort 上下文里擦
  64KB(几百 ms)极危险。所以:

  正常启动: 若 dumptrace 块已被读出消费 → 健康上下文里擦干净(全 0xFF),备用
  故障发生: 异常处理器只做 ①抓寄存器/fault状态 ②只 WRITE 一条≤128B
  记录(不擦,快·安全) ③触发 PMIC 复位
  下次启动: 早期读 flash → 有记录 → 经 CAN 0x100(2帧128B)播出 → 解析脚本定位 →
  读出后再擦块备用
  - R5 抓:fault 类型(undef/prefetch/data abort)+ DFSR/IFSR/DFAR/IFAR + 出错
  PC/LR/SP + 几个栈寄存器/少量栈回溯。

  工具链的符号器 or 解析 .map)。

  难点 = M4

  M4 是独立核、独立 fault(CFSR/HFSR/MMFAR/BFAR)。难在:M4 通常不拥有 QSPI,且 RAM

  故障(data/prefetch abort)发生后:

  第一点:复位 + 防丢失

  要不要复位 —— 我建议自动 PMIC 复位,理由和你担心的正好相反

  你担心"复位了就不知道发生过故障"。但其实恰恰是复位后的 systemInfo 报文(0x100)
  告诉你发生过故障、是什么故障——你不靠"注意到它重启了"来判断,而靠那条报文。对比:

  - 不复位:雷达卡死在 abort 处理器里(当前默认就是死循环),一直无输出,要等人工断电
  才恢复;本次上电也发不出报文(系统已死),报文照样是下次上电才发。
  - 自动复位:雷达快速自恢复,重启后立刻播上一次的故障报文。测试同事看到"短暂无输
  出(=复位过)"+ 收到 systemInfo(故障类型/地点)——信息更全、还自愈。

  所以复位不会让故障"消失",报文才是判据。自动复位 + 下面的保留机制 = 最优。

  防丢失:别"读完就擦",改成"保留 N 个周期 + 每次上电都重发"

  你的核心担忧对:读出即擦 = 没录到就永久丢。修正策略:

  1. 读出绝不擦。每次上电都把 flash 里的故障记录重发一遍(甚至开机几秒内发 2–3
  次,防单帧丢)。于是有故障后,接下来每一次上电都是一次抓取机会,不是只有一次。
  2. 靠"上电计数"老化,而不是靠读出。N 个周期(比如 20)内没有新故障,才擦掉。

  你的"分两个 64B page"评估 + 更好的办法

  你想的方向(用 flash 结构来保留)是对的,但"128B
  分两页"解决不了跨多次上电的计数问题。更合适的是利用 **NOR
  flash"只写不擦也能追加"**的特性(擦=全 0xFF,写只能把 1→0),在这个 64KB
  块里分两区:

  0x3F0000 块(64KB,擦除粒度 64KB):
  ┌─ 记录区:几个固定槽(比如 4 槽 × 256B)────────────────┐
  │   每槽 = magic + 序号 + bootTick + R5 故障负载 + CRC      │
  │   故障处理器写"第一个空槽"(只写,不擦)→ 保留最近 4 次故障 │
  ├─ 上电计数区(append-only tick 日志,剩余空间)───────────┤
  │   每次上电写 1 个字节 0x00 到第一个 0xFF 位置             │
  │   非 0xFF 字节数 = 自上次擦除以来的上电次数(=当前 bootTick)│
  └──────────────────────────────────────────────────────┘

  为什么这样最好:
  - 计数不需要每次擦——每次上电只追加 1
  字节(0xFF→0x00),无擦除、几乎无磨损、极快。
  - 记录不需要每次擦——故障处理器只往空槽写(块在老化后已擦干净)。
  - 老化规则:当前bootTick − 最新记录的bootTick ≥ N 才擦整块。即"距最后一次故障已
  N 个上电周期才清"——一次新故障会刷新窗口,完全是你说的"20
  个周期没再发生才清掉"。
  - 多槽=保留最近几次故障历史,新故障来了也不会被旧记录挡住(单槽 first-win
  会挡)。4 槽够用,64KB 空间绰绰有余。

  CAN 侧:0x100 仍是 2×64B 两帧(和 0x200/0x201
  一样的拆法),每次上电把"最新一条记录 + 故障历史摘要(共几次/类型)"打进
  128B。这跟 flash 的多槽保留是两回事,别混。
